# Инструкция по скрипту `npfp_financing`

## 1. Что делает скрипт

Скрипт — это один большой SQL-запрос (WITH ... SELECT), который **строит витрину показателей финансирования национальных проектов (НП/ФП)**: по каждому коду НП/ФП (`npfp_code`) считается набор фактов (`fact_code`) в разрезе источника финансирования (`fin_source_id`) — сколько денег утверждено, выделено, изменено, исполнено и т.д.

Результат — плоская таблица с колонками:

| Колонка | Смысл |
|---|---|
| `hash` | md5-хэш от ключевых полей строки — используется для отслеживания изменений (типовой паттерн для витрин/Data Vault, чтобы понять, что запись реально поменялась) |
| `mart_du` | `now()` — дата/время расчёта витрины |
| `actuality_date`, `calendar_start_date` | дата актуальности данных (берётся из `act_date`) |
| `calendar_lvl` | зашит константой `3` — уровень календаря (квартал, судя по контексту дат) |
| `npfp_code` | код национального/федерального проекта |
| `fin_source_id` | источник финансирования (см. п.4) |
| `fact_code` | код показателя (см. п.5) |
| `fact_name` | человекочитаемое название показателя |
| `value` | значение, млн руб. или % |

## 2. Общая архитектура запроса

Запрос — это цепочка CTE (`WITH ...`), логически разбитая на **3 больших блока по источнику финансирования**, а в конце всё объединяется через `UNION` и попадает в финальный `SELECT`.

```
act_date                     -- параметры дат для всего скрипта
├── блок fs_fb   (~fs_1…fs_9)   -- федеральный бюджет
├── блок fs_mbt  (~fs_1…fs_9)   -- межбюджетные трансферты
└── блок fs_vni  (~fs_14…fs_18) -- внебюджетные источники
        │
        ▼
   UNION всех CTE → финальный SELECT с hash и метаданными
```

Блоки `fs_fb` и `fs_mbt` почти дословно дублируют друг друга по структуре (те же fact_code `fs_1`–`fs_9`), но с разными фильтрами на источник. Это стоит иметь в виду при доработках: если меняется логика в одном блоке, скорее всего похожее изменение нужно и в "зеркальном" блоке.

## 3. Блок `act_date` — параметры запуска

```sql
act_date AS (
	SELECT
		2026::int2 AS "year"
		,'2026-07-01'::date AS actuality_date_1
		,'2026-07-01'::date AS actuality_date_2
		,'2026-01-01'::date AS state_date_1
		,'2026-07-01'::date AS state_date_2
)
```

Это единственное место, где **должны** задаваться отчётный год и даты. При запуске за новый период это первое, что нужно менять:

- `year` — отчётный год.
- `actuality_date_1` — дата актуальности справочника `nsi_npfp` и таблицы `rpp_bc_18` (границы периода).
- `actuality_date_2` — дата актуальности паспортных данных `rpp_fs_tpbfs_18`.
- `state_date_1` — дата "на начало периода" для `reestr_sbr` (обычно 1 января года).
- `state_date_2` — дата "на текущий момент" для `reestr_sbr`.

⚠️ **Важно (грабли скрипта):** несмотря на наличие блока `act_date`, по коду разбросаны **захардкоженные даты**, которые с ним не связаны и их нужно руками находить и обновлять при каждом пересчёте:
- `'2026-07-13'` (актуальность `reestr_sbr` и `f_0503811`) — встречается в нескольких CTE (`fs_2_t1`, `fs_2_t2`, `fs_8_t1`, `fs_8_t2`, `fs_2_*_mbt`, `fs_8_*_mbt`).
- `'2026-07-16'` — актуальность `fpr_18` в `fs_16_t1_vni`.
- `'2026-01-01'` — используется напрямую (не через `act_date`) в `fs_14_t1_vni`/`fs_14_t2_vni`/`fs_16_t1_vni`.
- `'2026-07-01'` — используется напрямую в `fs_7_t1` и в `fs_16_t1_vni`/`fs_16_t2_vni` вместо `ad.actuality_date_1`.

Это несогласованность в самом скрипте (не ошибка интерпретации, а факт кода) — при актуализации нужно проходиться по всем таким местам вручную.

## 4. Источники финансирования (`fin_source_id`)

| `fin_source_id` | Расшифровка | Как определяется в источниках |
|---|---|---|
| `fs_fb` | Федеральный бюджет (все источники) | `reestr_sbr.col_19 = '3'`; для паспортов — `SourceName = 'Федеральный бюджет, всего'` |
| `fs_mbt` | Межбюджетные трансферты (часть федерального бюджета) | `reestr_sbr.col_14 IN ('500','560','570')` |
| `fs_vni` | Внебюджетные источники | `fin_source_code = '40'` в `rpp_fs_tpbfs_18` / `fpr_bt_18` |

## 5. Показатели (`fact_code`)

| Код | Название (`fact_name`) | Есть в блоках | Формула / источник |
|---|---|---|---|
| `fs_1` | Расходы ФБ, утв. Федеральным законом № 540-ФЗ | fb, mbt | `SUM(col_20)` из `eb_bp.reestr_sbr` на `state_date_1`, `col_19='3'` (fb) / `col_19='2' AND col_14 IN ('500','560','570')` (mbt) |
| `fs_2` | Выделено средств по СБР | fb, mbt | `SUM(col_20)` из `reestr_sbr` на `state_date_2` / `actuality_date = '2026-07-13'`. В mbt считается как `value_1 − value_2 − value_3` (учитывает уменьшение по кодам 560/570 с `col_19='4'`) |
| `fs_3` | Объём изменений СБР к 540-ФЗ | fb, mbt | `fs_2 − fs_1` |
| `fs_4` | % изменений СБР к 540-ФЗ | fb, mbt | `(fs_2 / fs_1) * 100 − 100` |
| `fs_5` | Расходы ФБ по паспортам ФП | fb, vni | `SUM(Value2026)` из `eb.rpp_fs_tpbfs_18` (в fb — `SourceName = 'Федеральный бюджет, всего'`, в vni — `fin_source_code = '40'`) |
| `fs_6` | Отклонение паспорта от СБР | fb | `fs_5 − fs_2` |
| `fs_7` | Структура, % к СБР | fb (только верхний уровень `t1`) | зафиксировано `= 100`. Реальный расчёт (`fs_7_t2`, доля кода в общей сумме) **закомментирован в коде** — сейчас не считается |
| `fs_8` | Исполнено средств | fb, mbt | `SUM(col_12)` из `eb_bp.f_0503811` (в mbt — доп. фильтр по КБК подстроке 18-20 знака: виды расходов `511,512,521,522,523,524,530,540`) |
| `fs_9` | % исполнения бюджета | fb, mbt | `(fs_8 / fs_2) * 100` |
| `fs_14` | Расходы ФБ по паспортам на начало года (01.01) | vni | `Value2026` из `rpp_fs_tpbfs_18` на `01.01`, `fin_source_code = '40'` |
| `fs_15` | % изменений расходов ФБ | vni | `(fs_5 / fs_14) * 100 − 100` |
| `fs_16` | Исполнено расходов | vni | `cash_execution_total` из `eb.fpr_bt_18`, `fin_source_code = '40'` |
| `fs_17` | Объём изменений расходов ФБ | vni | `fs_5 − fs_14` |
| `fs_18` | % исполнения к паспорту ФП | vni | `(fs_16 / fs_5) * 100` |

## 6. Паттерн `t1` / `t2` — самое важное для понимания скрипта

Почти каждый "базовый" показатель (`fs_1`, `fs_2`, `fs_5`, `fs_8`, `fs_14`, `fs_16`) считается **дважды**, в двух CTE с суффиксами `_t1` и `_t2`:

- **`t1`** — детальный уровень: `npfp.npfp_parent_code IS NOT NULL`, код НП/ФП берётся как есть (`col_10 AS npfp_code`). Это конкретные федеральные проекты внутри национального проекта.
- **`t2`** — агрегированный (родительский) уровень: `npfp.npfp_parent_code IS NULL`, код обрезается до первого символа (`LEFT(col_10, 1) AS npfp_code`) и данные суммируются по группе. Это сам национальный проект целиком.

Затем `t1` и `t2` объединяются через `UNION` там, где на их основе считаются производные показатели (`fs_3`, `fs_4`, `fs_6`, `fs_9` и т.д.), и то же самое объединение попадает в финальный `SELECT`.

Отсюда следует: `nsi_npfp.npfp_code` — иерархический справочник, где однобуквенный код — это национальный проект, а более длинный код с непустым `npfp_parent_code` — федеральный проект внутри него.

## 7. Финальный `SELECT`

```sql
SELECT DISTINCT
  md5(actuality_date_1 || '3' || npfp_code || fin_source_id || fact_code || fact_name || value) AS hash,
  now() AS mart_du,
  actuality_date_1 AS actuality_date,
  actuality_date_1 AS calendar_start_date,
  3::int2 AS calendar_lvl,
  npfp_code, fin_source_id, fact_code, fact_name, value
FROM ( UNION всех CTE ) AS fin, act_date AS ad;
```

Он просто объединяет (`UNION`) все посчитанные CTE в одну таблицу фактов и добавляет технические поля (хэш, дату расчёта). Если нужно добавить новый показатель — CTE считается отдельно и добавляется ещё одной веткой `UNION` сюда же.

## 8. На что обратить внимание при поддержке скрипта

1. **`fs_7_t2` закомментирован** (строки ~270–284) — показатель "структура в % к СБР" на детальном уровне сейчас не считается, есть только заглушка `100` для верхнего уровня.
2. **Хардкод дат вне `act_date`** — см. п.3, при пересчёте за новый период надо руками искать и менять `'2026-07-13'`, `'2026-07-16'`, `'2026-01-01'`, `'2026-07-01'`.
3. Комментарий в `fs_16_t1_vni`: `actuality_date` из `fpr_18` **"надо менять на каждый квартал (меняется в зависимости от графика загрузки данных в СМЭВ)"** — то есть это не автоматизируемая дата, а зависящая от внешнего графика загрузки.
4. В `fs_7_t1` есть комментарий автора `--понять бы что за дата` — то есть смысл конкретной даты `'2026-07-01'` в этом месте не до конца задокументирован даже автором скрипта, стоит уточнить у коллег перед изменением.
5. В `fs_8_*` есть отметка `-- изменен на col_12 (была col_14)` — колонка расчёта исполнения менялась, при вопросах "почему не col_14" это объясняет историю.
6. Блоки `fb` и `mbt` для `fs_1/fs_2/fs_3/fs_4/fs_8/fs_9` дублируют друг друга почти 1-в-1 с разными фильтрами — при правке логики проверяйте оба места.
